### In-app game data setup (`SetupActivity`)

The launcher now starts the game when data is present, otherwise offers:

- **Download from Steam** — the user signs in to their own account; JavaSteam 1.8.0's
  depot downloader fetches app 2732960's Windows depot (what `scripts/get-assets.sh` pulls
  with steamcmd). Steam Guard via mobile approval, app code or email code. Credentials and
  the session token stay in memory only.
- **Import from folder** — `ACTION_OPEN_DOCUMENT_TREE`, no storage permission; skips
  Windows-only files; accepts the install folder or a parent up to two levels above it.
- **Buy on Steam** — store page.

Data goes to `<external app files>/GeneralsZH`; `/sdcard/GeneralsZH` (adb push) still wins
when present. A `.gx_setup_complete` flag guards against an interrupted download/copy
leaving `INIZH.big` behind without the rest. The directory reaches `SDL3Main.cpp` through
`GX_GAME_DATA_DIR` (set with `Os.setenv` before SDL loads). The APK bundles the Liberation
fonts (`stage-fonts.sh`), copied next to the data because the engine loads `fonts/*.ttf`.

JavaSteam declares its chunk decompressors `compileOnly`, so the app adds `org.tukaani:xz`
and the `zstd-jni` **aar** (the jar only carries desktop natives).

CI run 3 got through the whole native build (libmain, DXVK, adrenotools) and failed at
`compileDebugJavaWithJavac`: `package okhttp3 does not exist`. JavaSteam's POM declares
OkHttp (and all its other deps) with runtime scope, so Gradle keeps them off the compile
classpath; the earlier local javac check had used every runtime jar and hid it. Fixed by
using JavaSteam's default `SteamClient()` configuration instead of a custom OkHttp client
(adding OkHttp directly would pull `okhttp-android` next to JavaSteam's `okhttp-jvm`).
The local check now compiles against exactly the compile-scope jars. The zstd-jni aar's
arm64 library is already 16 KB aligned.

Validation so far: Java sources compile against the Android 14 framework
(Robolectric `android-all`), SDL 3.4.2's Java glue and JavaSteam 1.8.0 with no warnings.
Not yet run on a device.

### C&C Online: "Online" could never reach the login screen

Traced the online entry path without the C&C Online launcher (which on PC redirects DNS):

- `StartPatchCheck()` first resolves `servserv.generals.ea.com`. It has no DNS any more, so
  `cantConnectBeforeOnline` was set, the "cannot connect" box shown, and the game returned
  to the menu. Every Android (and launcher-less) attempt ended there.
- `GSI_DOMAIN_NAME` only rewrites hostnames the GameSpy SDK builds. Some of those don't exist
  on C&C Online: `ccgenzh.ms6.server.cnc-online.net` (server browser),
  `ccgenzh.master.…` (QR2 heartbeats), `ccgenzh.available.…` — verified NXDOMAIN, while
  `master.`, `peerchat.`, `gpcm.`, `gamestats.`, `http.` all resolve.

Fix, mirroring the C&C Online client's own redirect table (xan105/CnC-Online, MIT,
`src/online.h`: servserv → `http.server.cnc-online.net`, `ccgenzh.ms6` → `master.`):
new `OnlineServiceHosts.h`; `cmake/gamespy.cmake` passes `RTS_GAMESPY_SERVER_NAME` to game
code; servserv lookup, base URL, gamestats, players-online and peerchat local-IP hosts use
it; before `peerInitialize()` the SDK's own override hooks (`qr2_hostname`,
`GSIACHostname`, `SBOverrideMasterServer`) point at the master host. Standalone compile test
against the SDK headers with and without the define prints the expected hosts.

Not reachable from the build environment (network policy), so the servserv files under
`http.server.cnc-online.net` could not be fetched to confirm the path; needs an on-device
test. Known remaining gap: the SDK hardcodes peerchat port 6667 (the PC client retries
16667 when an ISP blocks 6667); on such mobile networks use Wi-Fi.

### Steam sign-in: "in.dragonbra.javasteam.util.crypto.CryptoHelper"

First on-device report (release r7): "Download from Steam" failed immediately with
`Steam sign-in failed: in.dragonbra.javasteam.util.crypto.CryptoHelper`. Root cause:
CryptoHelper's static initialiser loads `org.bouncycastle.jce.provider.BouncyCastleProvider`
and JavaSteam does not bundle it (its README asks apps to add `bcprov-jdk18on`), so the
class failed to initialise; the dialog showed only the error's message, which is the class
name. Reproduced on the JVM with JavaSteam 1.8.0's runtime jars (ExceptionInInitializerError).

Fix: add `org.bouncycastle:bcprov-jdk18on:1.83` (the version JavaSteam tests with) and,
before JavaSteam loads, replace Android's platform "BC" provider (a stripped copy that would
otherwise keep the name and lack algorithms) with the full one. Verified on the JVM with a
stripped provider pre-registered as "BC": after the swap CryptoHelper uses BouncyCastle, and
SHA-1 and AES/CBC/PKCS7Padding resolve. Also: the download thread now catches `Throwable`
(an Error left the UI stuck busy), failures show the root cause's type and message, and the
release APK is named `GeneralsZH-android-rN.apk`.

### Steam sign-in: AsyncJobFailedException; saved login; background download

r8 fixed CryptoHelper; the next on-device report was
`Steam sign-in failed: AsyncJobFailedException`. JavaSteam raises it when a job is started
while `isConnected` is false or when Steam answers with JobFailed. JavaSteam 1.8.0's
WebSocketConnection runs a watchdog that disconnects after 30 s without a *binary* frame
(Ktor consumes ping/pong internally, so keep-alives never reset it). A Steam Guard approval
or code entry routinely takes longer; the session drops silently and the next
authentication request fails. Upstream rewrote the watchdog in June 2026 (`c4476fa`), which
is not in any release. Fix: connect over TCP (no such watchdog) and fall back to WebSocket
only when TCP never connects (networks blocking Steam's TCP ports).

Also, as requested:
- **Saved login.** Credential sign-in now asks for a persistent session; the account name
  and refresh token are stored AES-GCM-encrypted with an Android Keystore key
  (`SteamLoginStore`); later downloads sign in with the token (no password, no Steam
  Guard). "Sign out of Steam" deletes it; a rejected token is deleted automatically.
- **Background download.** `DownloadService` runs the download as a dataSync foreground
  service with a progress notification and a Pause action, holding a partial wake lock
  and a Wi-Fi lock. It survives the screen turning off and the app being swiped away.
- **Resume.** A pending flag stays set until the download completes, the user pauses, or a
  non-recoverable error (sign-in, ownership) occurs. START_STICKY restarts resume with the
  saved login, and opening the app with the flag set resumes too. DepotDownloader 1.8.0
  validates existing files when no previous manifest is recorded and fetches only missing
  or damaged chunks, so a resume continues where it stopped. Cancelling polls the completion
  future (closing the downloader does not complete it, so `awaitCompletion()` would hang).
- **Orientation.** The setup/launcher screen follows the device rotation (`fullUser`,
  buttons become a full-width column in portrait); the game activity is locked to
  landscape (`sensorLandscape`, either way up).

### Launcher: app updates, game file updates, cache reset

- **Check for app updates** (`AppUpdater`): reads GitHub's `releases/latest` for this repo,
  parses `android-r<N>` and compares N with the installed versionCode; a newer APK is
  streamed into a `PackageInstaller` session and committed (Android shows its confirmation;
  first use asks to allow "Install unknown apps"). Signature conflicts get a clear message.
  Verified against the live API from the build environment: r9 parsed, update offered to r8
  and not to r9; the asset URL redirects to a pre-signed download that serves GET (HEAD is
  rejected by the pre-signed URL, which the app does not use).
- **Update game files**: re-runs the Steam depot download into the same directory; every
  file is validated and only changed or damaged chunks are fetched (the "patcher" for the
  Steam copy). The completion flag is cleared first, so an interrupted update resumes like
  a download instead of leaving a half-updated install marked complete.
- **Clear caches**: deletes DXVK pipeline caches (`*.dxvk-cache`), Mesa's shader cache
  (`$HOME/.cache`) and the user `Maps/MapCache.ini`; the game rebuilds them.
- Launcher buttons are now a grid: one column in portrait, three in landscape.

Signing secrets still need adding by the repository owner (secrets cannot be created from
the tools available here); until then each CI build is signed with a different throwaway key
and in-app updates report the signature conflict.

## 2026-09-28: Mods (Super Patch, custom mods) and C&C Online files

### How mods load

The engine takes one `-mod <folder>` (CommandLine.cpp `parseMod`) and
`ArchiveFileSystem::loadMods()` loads every `*.big` under it recursively with overwrite;
`getFileListInDirectory` collects paths into a sorted set and follows symlinks
(`directory_iterator::is_directory`). So mods live untouched in `files/Mods/<id>/files/`,
enabled ones are symlinked into `files/ModsActive/NN_<id>` (load order = enable order, later
wins), and GeneralsXZHActivity appends `-mod <ModsActive>` when any mod is on. The retail
data is never modified.

Custom mods can ship loose files, which `-mod` does not load, so `BigArchiveWriter` packs
them (paths relative to the folder holding Data\/Art\/Window\...) into one BIG, following
`Win32BIGFileSystem::openArchiveFile`'s layout (BIGF, LE size, BE count/header size, BE
offset/size + NUL-terminated backslash path). Verified by packing a sample mod and parsing
it with an engine-equivalent reader: paths, offsets and contents match. Zip import rejects
entries that escape the mod folder.

### Super Patch

TheSuperHackers/GeneralsGamePatch has no releases (players build it with the Windows-only
Mod Builder). `build-super-patch.yml` builds upstream main on a Windows runner and publishes
`superpatch-<sha>` (English Full and Core packs, not marked latest so the APK updater is
unaffected). The Mods screen downloads the newest Full pack and installs it as a toggle.

### Other mods

Contra, ShockWave and Rise of the Reds are listed with links (their own sites and terms);
the user downloads and imports them with "Add mod" (folder or .zip). Not tested on Android.
GenPatcher is not supported: Windows-only, and its fixes target the retail executable.

### C&C Online files

"C&C Online: latest files" fetches what the game's patch check reads from servserv
(MOTD-english.txt, config.txt, english-65540.txt, maps-65536.txt) from
http.server.cnc-online.net, shows the MOTD and offered files, and installs .zip/.big
entries as mods (.exe installers are listed as unusable). The app's network security config
permits cleartext only for cnc-online.net, which serves these over plain HTTP.

### Mod load order

The first Super Patch build (`superpatch-6c7f40d`) ships `600_899_SuperPatch_Optional*.big`,
`600_900_SuperPatch_Core*.big` and `600_901_SuperPatch_RecoveredTextures.big`, named for the
game folder, where the first archive to provide a file wins. The `-mod` folder loads in the
same sorted order but overwrites, so the last one wins, which would let the core files hide
the optional art. `ModManager.prepare` now moves every archive to the mod root as
`NNN_<name>` with descending numbers before packing loose files, so each mod keeps its
intended priority and `zz_loose_files.big` still loads last.

## 2026-09-28: Crash logs players can send

Reports of crashes at startup and mid-game came with no evidence: the engine's output
only reaches logcat, which players without adb cannot read.

- `SDL3Main.cpp`: the logcat pump also writes each line to `files/logs/game.log`
  (previous run kept as `game-prev.log`, 16 MB cap after which only error lines are
  kept, timestamps in seconds since start). A signal handler (SIGSEGV/BUS/FPE/ILL/ABRT/
  TRAP, on an alternate stack for the main thread) writes the signal, fault address,
  pc/lr and an `_Unwind_Backtrace` of `lib+offset (symbol+offset)` frames, then hands
  the signal back to the previous handler so debuggerd still runs. Tested on the host:
  it unwinds through the signal frame into the faulting function and the process still
  dies with the original signal.
- `CrashLogs.java` + launcher **Save logs** button: one text report (device, SoC, RAM,
  app version, enabled mods, `ApplicationExitInfo` history, `ReleaseCrashInfo.txt`,
  `Options.ini`, both logs trimmed to head+tail, app logcat) saved via the document
  picker. After an abnormal exit (crash, low-memory kill, ANR, `_exit(1)` from
  `ReleaseCrash`) the launcher says what happened and offers to save.
- CI publishes `GeneralsZH-symbols-<tag>.tar.xz` (unstripped jniLibs) with each release
  so backtrace offsets resolve to source lines.

## 2026-09-28: First device crash report (S25 Ultra, Adreno 830)

The new Save logs report pinpointed the crash on the first try: SIGSEGV (fault address
0x2000000001) in `dxvk::DxvkMemoryAllocator::createAllocation`, reached from
`D3D9ConstantBuffer::AllocSlice` during an ordinary mesh draw (`DX8Wrapper::Draw`),
symbolized with the release's `GeneralsZH-symbols-android-r14.tar.xz`.

The log explained why: from the moment the game window turned landscape, DXVK's presenter
logged `Got VK_SUBOPTIMAL_KHR, recreating swapchain` on every frame (849 times in 40 s).
Android returns SUBOPTIMAL whenever the swapchain's preTransform (DXVK always uses
IDENTITY) differs from the display's rotation hint, which is every frame on a phone
(natural orientation portrait) in landscape. Upstream only ever ran on a 2800x1752 tablet
(natural landscape), so it never saw this. Rebuilding the swapchain every frame churned GPU
memory until the allocator fell over.

- `Patches/dxvk-android-suboptimal.patch` (applied by `cmake/dx8.cmake` after
  `dxvk-android.patch`, both idempotently): on Android the presenter treats SUBOPTIMAL as
  usable; the compositor rotates the image. OUT_OF_DATE still recreates the swapchain.
- The log also showed the game device being created with a portrait backbuffer
  (1440x2939) because the activity starts before its landscape rotation lands; the
  landscape image was squeezed into it until a reset ~9 s later (the "zoomed" look, and
  touch mapped through the wrong rectangle meanwhile). `SDL3Main.cpp` now waits (up to
  3 s) for the landscape surface before creating the device.
- `TouchKeyBar.java`: collapsible on-screen keys for what gestures cannot do (Esc menu,
  latching Shift/Ctrl/Alt, Q, Space, control groups 1-5), injected through SDL's Android
  key path. The gesture translator itself (tap/drag-box/long-press/two-finger pan/pinch)
  is unchanged.

## 2026-09-29: Autosave, backup, performance defaults, haptics, LAN, text size

- **Background autosave**: SDL delivers WILL/DID_ENTER_BACKGROUND on the engine thread and
  lets one more frame run before blocking (SDL block-on-pause), so the first paused frame in
  `SDL3GameEngine::update` saves a skirmish/campaign match (never multiplayer or replays, as
  the quit menu) to `Save/AndroidAutosave.sav`. The launcher says once where to find it.
- **Backup & restore** (`PlayerData`): zips the whole user data folder (saves, replays, added
  maps, Options.ini and other prefs) through the document picker, restores with a zip-slip
  guard. **Replays**: import .rep files, save a copy of one to share.
- **Performance defaults**: without a chosen resolution, panels above 1080 lines render at
  1080 lines in the panel's shape (2340x1080 instead of 3120x1440 on an S25 Ultra; the
  pillarbox upscales). Settings offers Auto / Native / smaller. **Frame rate cap** 30/45/60
  (`GX_RENDER_FPS` -> FramePacer; render only, the simulation's 30 Hz is unchanged, so replays
  and multiplayer are unaffected). **Overheat protection**: a PowerManager thermal listener
  caps rendering at 30 FPS from THERMAL_STATUS_SEVERE until it cools (`nativeSetThermalFpsCap`).
- **Haptics**: key bar presses, long-press and two-finger tap (engine calls the activity's
  `gxHaptic()` through JNI), switchable in Settings.
- **LAN**: LAN lobbies discover each other by UDP broadcast, which many phones drop without a
  `WifiManager.MulticastLock`; held while the game is in the foreground. Untested on devices.
- **Text size** (Settings): Options.ini `ResolutionFontAdjustment` 85/100 (game default 70).
  The control bar itself cannot be enlarged without reworking the engine's UI layout.
- **Turnip for Adreno 8xx: not shipped.** The only Turnip build with a8xx support
  (K11MCH1 v26.0.0-rc08, `a8xx_0x5_handle`) is described by its author as "very beta and
  hacky", failing for non-OpenGL (Vulkan) games and able to leave the stock driver broken
  until reboot. Adreno 8xx keeps the stock Qualcomm driver; revisit when a8xx Turnip matures.
